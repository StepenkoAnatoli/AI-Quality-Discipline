## 2. Benchmark lifecycle, as implemented

Task preparation (allowlisted files, pinned prompt and workspace hashes) → host setup on a fresh `ubuntu-24.04` runner with per-condition OS users, a fresh HOME per run and network limited to the Anthropic API → seal a random two-run order → pre-prompt isolation checks against the live server → session through the OpenCode 2.3.2 HTTP API, with the skill attached through the API in treatment only → export checks (model, activation, contamination, provider errors) → run validity → lock the agent accounts and shred the credentials → only then decode the hidden pack → per-test Docker scoring with a nonce → encrypt and upload → a public status summary. This chain is VERIFIED by reading `phase3-ab-run.yml` and the harness, and by the step timings of run 44980786824. Its runtime behaviour (activation evidence, contamination scans) is only as good as the unit-tested checks plus the runs' own success status.

**Blinding.** `blind_packet.py` exists, but no blind scoring or secondary ratings are reported for any A/B run. INFERRED: the secondary process outcomes (verification, scope, reporting quality) were never measured. AB-RESULTS.md reports only hidden scores, test counts and tool calls.

**Validity gaps found (not defects in fail-closed scoring; they arise from how non-valid slots enter the comparison):**

1. **Scope violations are exclusions.** `run_status.py` marks a run INVALID when an immutable file changed, and the agent's permissions allow edits to package modules other than the mutable file (only `TASK.md`, `README.md`, `opencode.jsonc` and `tests/baseline/*` are denied). A control run that breaks scope would therefore leave the comparison instead of counting against the control, even though scope control is one of the skill's rules. VERIFIED (code). Proposed v3.3 change: DESIGN.md §5.
2. **Candidate-caused crashes are exclusions.** A wrong solution that exhausts memory (OOM kill), calls `os._exit` or raises `SkipTest` makes the evaluation INVALID by design. That is right as an anti-forgery rule, but `analyze.py` then drops the slot. VERIFIED (tests `test_process_killed_before_result_is_invalid` and `test_skip_raised_by_candidate_is_invalid`). The new tier analysis carries every such slot into worst/best-case bounds, and a decision that depends on them is inconclusive (implemented).
3. **The evidence behind the published numbers is ephemeral.** 1-day artifact retention, no committed machine-readable results. VERIFIED.
4. **Only the mutable file is scored, and new stray files are recorded but never reported.** "Unnecessary changes" is not measured. VERIFIED.

The old runner must not be reused under any circumstances: the current `run_checks.py`/`score_run.py` pair supersedes it.

Review of the **current** skill (`d050d00f…`), against the questions in the brief:

- *Regression testing.* "Add or update tests for meaningful behavior changes" does not ask the agent to show that a new test fails on the old code. That is the step that separates a relevant test from a decorative one; per AB-RESULTS, the NEW-01 treatment run did it unprompted. A candidate improvement for a later, separately evaluated version.
- *Verification vs running commands.* Covered well ("A command that starts is not a passing check"; inspect output and exit status).
- *Scope.* "Plan the smallest coherent change" and "Avoid unrelated cleanup and speculative redesign" are reasonable. On tasks that need a rewrite (NEW-03 and NEW-04 asked for one) they could in principle suppress necessary restructuring, which would be an H2 mechanism. No evidence either way.
- *Overhead.* 88 lines. The treatment cost 13–36% more per run (unverified figures) and wrote more tests, with no measured correctness gain at this difficulty.
- *Do not rewrite now.* The current skill must first get a baseline on tasks that discriminate (DESIGN.md §12).
